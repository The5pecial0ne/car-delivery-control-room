# Build log

Notes on how we built this with coding agents, kept as we go so the demo video can tell the real story.

## Saturday 24 October

**Plan.** We asked Claude Code to read the brief and the repo and to ask us questions before planning. We chose the on-the-road area because the brief's own example (a warning light on the motorway) is about it, and because a simulated driver makes a demo that feels alive. We kept the starter app instead of starting over.

**Step 1: agent backend.**
- The agent's work lives in two new tables, `agent_cases` and `agent_steps`, so the dataset snapshot stays untouched. Every lookup, message, proposal and decision becomes a step, and that is the trace.
- Approvals are built in from the start. `lib/agent/policy.ts` lists every kind of change the agent can propose, each with its own switch (`needs_approval` or `auto`), so autonomy can grow one action at a time.
- The agent has no tool for contacting customers at all. It can only draft a message for a person to send. We liked that better than a rule in the prompt that the model might ignore.
- The simulated driver is a second, smaller model. It gets a private scenario (where they really are, what the dashboard shows) that the agent cannot see, so the agent has to ask.
- Hand-overs are checked. If the agent tries to hand over without a headline, with facts that are not a list, or with an action that does not exist, the tool refuses and tells it to fix that.
- We wrote a plumbing test (`npm run agent:test`) with a scripted stand-in for the model, so we can check the state machine without spending credit.
- What we threw away: the first version of the driver lookup scanned every job and filtered in code. We moved the filter into the database query.

**Step 2: the on-the-road agent (first half, before we had model access).**
- Pretend outside services in `lib/agent/services.ts`: roadside help, tow quotes, ferries, hotels and a delay-against-promise check. Prices are made up but stable (seeded by the input), so the demo can be rehearsed. Where the dataset already has a record (the sold-out ferry on CD-420299) the tool returns it with its id, so it can be cited.
- Three demo scenarios in `lib/agent/scenarios.ts`, picked to show both halves of the job: two cases that need a person (a warning light on a Bentley, a sold-out ferry) and one the agent should close by itself (a ferry queue that starts moving).
- Caught while testing: the agent would have used the wall clock as "now", but the data is a snapshot from 21 October. The case now starts with the snapshot time.
- Caught while reading the data: the simulated driver only heard `driver_chat` messages, but some drivers write in `support_chat` or email. It now hears every public message to or from the driver.

**Step 3: the "Needs you" desk.**
- The home page is now a desk, not the board. Cases are grouped by who has the ball: waiting for you, agent is on it, handled without you. The old board of lanes moved to "All orders".
- Each case reads top to bottom the way a person decides: the headline, what happened, the agent's suggestion with Approve, Do something else and Reject, then what it found with a source on every fact, what is still unknown, and the full story underneath.
- Sources you can follow: a fact the driver told the agent links to that exact message in the story below. Made-up quotes are marked "Quote (simulated)" so nobody mistakes them for real records.
- The customer message is a draft the person edits and sends on approval. The page says plainly that the agent never sends it.
- Caught in review: a person could write to the agent while it was still mid-run, and the running loop would then overwrite the conversation and lose that message. The message box is now locked while the agent works, and the server refuses with a clear reason.
- We tried the case headline in the urgency colour first. A full orange sentence shouted, so the colour now lives in the small chips and the headline stays black.

**Step 2, second half: tuning the agent on real runs.** Once we had model access we ran the three demo cases again and again, read every trace, and fixed what we saw. The rule we kept to: when the model got something wrong that plain code can get right, we moved it into a tool or a check instead of adding more words to the prompt.

- *It did date maths in its head and got it wrong.* On the sold-out ferry it called Saturday "Friday", and once it said the later sailing needed one hotel night when it needs two. We added `plan_sailings`, a tool that works out the whole plan for every sailing that is left: when the driver reaches the terminal, whether they make check-in, which nights need a hotel, and when the car reaches the buyer against the promise. Every time now also comes with a local time and the weekday. After that the dates were right in every run.
- *It contradicted itself.* One hand-over had the headline "may miss the Oct 27 promise" and a customer message saying "well ahead of your Oct 27 window". `estimate_delay_impact` now takes the planned arrival and answers inside or outside the promise, with hours to spare. That check used to need a driver-app ETA, so it said "no promise on file" before pickup.
- *It said a promise was "already missed" before the window had even opened.* We added a short section to the prompt on time: compare in UTC, talk in local time, and "will miss" is not the same as "already missed".
- *It cited sources that did not back the fact.* Tow prices were cited as "the driver said so", and "Bentleys often have their own assistance" was cited to a driver message. The hand-over tool now checks every source against what the tools actually returned on this case. If it has never seen a source, it sends the hand-over back. It caught a citation to `plan_sailings` (a tool, not a record), a headline with an order id in it, and headlines that were too long. The refusals stay in the story, so you can watch the checker do its job.
- *The tow quotes were random.* A tow from Munich to Hamburg came back as 47 km. Pretend services now know rough coordinates for every city in the dataset, so distances, prices and transit times look like the real map.
- *Our own demo scenario contradicted the data.* We had put the Bentley near Munich, but the order's tracking has it about 230 km from Hamburg. The agent noticed the mismatch, and that is how we found it. We moved the breakdown to Rasthof Göttingen on the A7.
- *It never asked the driver on the ferry case.* It took a three-day-old message as the answer. Now the prompt says that on a live case the agent always messages the driver before it hands over or closes, and asks what the driver can live with (how long they can wait, their train home), not only where they are.
- *It made promises nobody had approved.* "We'll arrange your return travel." "Customer informed." Neither had happened. We tightened this in two places. The prompt says only what a step shows has happened. And after an approval, the agent is told exactly which action was carried out and that nothing else in its summary was.
- *Approving a phone call made no sense.* "Call the customer" was marked "Done (simulated)", so the agent made up what the customer said. Actions a person does themselves now show "I did this" instead of Approve and ask "How did it go?". The agent picks up from what the person writes. In the test run it told the driver to hand over to Bentley's recovery team and closed the case.
- *It left a loose end on the case that went fine.* In the ferry queue case, operations had asked the carrier to move the car to a later crossing while things looked bad. The agent saw that the driver had checked in and closed the case, but left the request open, so it could still have moved the car later. This became our first automatic action. `withdraw_change_request` is switched to `auto` in `lib/agent/policy.ts`, so the new `take_action` tool lets the agent do it alone. The tool refuses every action that is not switched to `auto`. The autonomy switch we designed in step 1 now does something real.
- *The simulated driver drifted off script.* At temperature 0.7, and with the old "I'm stuck in the queue" messages in its history, the driver sometimes said it was still stuck when its private scenario says it is checked in. We told it the scenario is the truth as of now and overrides earlier messages, and lowered the temperature to 0.4. After that, three runs out of three stayed on script.
- `npm run agent:demo` clears the desk and runs all three cases side by side, for recording. `npm run agent -- <order> --approve --note="..."` runs a case and then answers its hand-over, so we can test the follow-up without clicking.

Where it ended up, on the same three cases: the Bentley case hands over "call the customer" with roadside, local-workshop and tow-to-Hamburg quotes, how long the driver can wait, and a ready-to-send customer message. The ferry case recommends the earlier sailing with one hotel night, checked against the promise, with the driver's agreement. The queue case confirms check-in with the driver, withdraws the stale change request by itself, thanks the driver and closes. About $4 of model credit went into all the tuning runs together.

**Step 5: ideas from Manas after seeing the screens.**
- *Risk as a countdown, not a red badge.* Every hand-over now has to list its deadlines: the last safe moment for the plan, hard cutoffs such as ferry check-in or the driver's train, and when the delivery promise is breached. Each one has a source. The checker refuses a hand-over without them unless it can wait. The case shows "2 h 57 min until the driver has to leave" with the full list underneath, and the desk card shows the next one. Each case runs on its own clock: it starts at the snapshot time and then moves with the real clock. So a case that has sat on the desk for twenty minutes really is twenty minutes closer to its deadlines.
- *Plan B while it waits.* The agent now prepares a fallback before it hands over: when to switch (tied to a deadline), what we would do, and the numbers. It does the real lookups for it. A new `find_backup_drivers` tool lists drivers who live near the place and are not on another job. They are marked as not asked, because the agent cannot contact them. The person can switch to plan B with one click.
- *Speed, cost or certainty.* Every option now carries when the car would arrive, what it costs and how certain it is (confirmed, quoted or uncertain). A switch on the case ranks the options by what matters most today, and the choice is remembered. Choosing another option tells the agent which priority made the difference. The ranking is plain code, so the agent cannot game it, but its own pick stays visible as "Agent's pick".
- *Site patterns.* `lib/agent/patterns.ts` reads the records every order already has (alerts, work items, missing documents, site visits) and groups the trouble by place and theme. Two or more different orders with trouble at the same place counts as a pattern. The site profile repeats the same thing on every order, so it can add to a pattern but never make one; we caught that when every Helsinki dealer lit up. Two real patterns came out: Velantora Helsinki (keys, gate and a car that was not there) and Calverona Hamburg (release papers and rejected pickup photos). The notice shows on the order and on its case, and `get_order` hands it to the agent.
- *Easy reading.* A switch in the sidebar sets the whole app in Lexend, with more space between letters, words and lines, no italics, and no text cut off with "…". It is remembered per browser and set before the first paint, so the page does not flash.
- *Caught while testing:* three cases at once hit OpenRouter's limit for new accounts (20 requests a minute), and two cases failed. The model client now waits and retries on 429 and 5xx answers. The simulated driver also slipped back into "still in the queue" once. It now gets a reminder of its private situation right next to the message it is answering, and that fixed it.

**Step 6: two stages, investigate then recover.** Manas's brief split the work into an investigation half and a recovery half. We checked the build against both. The recovery half was mostly there already. The investigation half had gaps: facts had no status, conflicts were not written down, there was no single key question, no timeline of planned against real, and no way to ask the pickup site. We kept one agent and made the two stages explicit, in its tools and on screen.
- `record_findings` is the investigation's output: the main problem, every fact marked confirmed, reported, planned or unknown (only unknown facts may go without a source), conflicts with both sides cited, the one key question and who can answer it, and the delivery timeline as planned, reported, confirmed, missed or projected.
- The order of work is checked in code, not just asked for in the prompt. `ask_person` and `close_case` refuse to run until findings are recorded, and again whenever the driver or the site has said something since the last findings. The agent's understanding visibly updates after each answer, and the case shows how many times it did.
- `ask_pickup_contact` calls the desk named on the order's pickup details. A simulated contact plays them, with its own private scenario, just like the driver. `get_site_history` exposes the site patterns as a tool.
- New demo case, "Car not at the pickup" (Velantora Helsinki). The customer's system says the car is at the branch, and reception cannot find it. The site desk knows it was moved to the Vantaa yard, with the keys in a key safe that opens only after a new release email. The agent treats the customer's system as reported, not confirmed. It asks the site, records the conflict and how it was settled, and plans around a driver who has 45 minutes left. The place also has a site pattern, which the case shows.
- The case screen now reads in two numbered stages. **1 Investigation** asks what happened, what is confirmed and what is still unknown. **2 Recovery** asks what we can do, what each option costs or breaks, how much time is left and what you approve. The agent's tool trace sits underneath as "Agent activity".
- Easy reading now uses OpenDyslexic, bundled with the app through `@fontsource/opendyslexic`. Its letters are already wide, so we dropped the extra letter spacing we had added for Lexend.

**Step 7: one control room instead of a case list.** Manas asked for the home page to show every order, split by whether a person has to look at it, with a timeline on every order.
- *Needs attention* sits in the middle. It uses the board's own rule (an order with attention items from `deriveAttention`), plus any order whose agent case is waiting for a decision or has stopped. Nothing else counts, so the home page and the board never disagree. Each card says what is wrong, why it needs a person, the next deadline (the case countdown when there is a hand-over, otherwise the order's decisive date) and what the agent already checked. Orders the agent has not looked at say so plainly.
- *Monitored · on track* is a fixed panel on the right that scrolls on its own. It holds everything else, grouped by stage with the moving cars first: reference, car, route, status, the next milestone and when the order last changed. On narrower screens it moves under the queue, and on a phone the whole page stacks.
- *A timeline on every order*, at the top of the case on the home page and at the top of the full record. It is built in `lib/present/timeline.ts` from records that already exist: the order's event log, its alerts, incidents and work items, other agents' proposals, its bookings and key dates, and the agent's case steps. Green is confirmed, red is a conflict or something that needs attention, teal is the agent, orange is a decision waiting, and grey is still to come. Every row also says so in words, and a small legend sits above it. Agent steps are shown on the case clock, the same clock the countdowns use, so the "Now" line and the deadlines agree. The timeline follows the same polling as the case, so a new agent step shows up without a reload.
- Nothing about the agents changed. The recovery screen, the approvals and the agent activity still sit under the timeline as before. Orders without a case show their full record there instead.
- Assumption: the brief pointed at `docs/investigation/*.md`, which does not exist in the repo, so we worked from the brief and the code.

**Step 8: a calmer design, and priority and Plan B that do real work.** Manas felt the control room looked scattered and generic, and asked for speed, cost and certainty, and Plan B, to work end to end.
- *What was already there:* the agent's hand-over has carried a plan B and scored options (arrival, cost, certainty) since step 5. A switch ranked them by speed, cost or certainty. But it only appeared on cases with a hand-over, only reordered the list, and there was no Plan B at all for an order the agent had not opened.
- *Plan B is prepared for every order that needs attention,* the moment it is opened. `lib/agent/plan-b.ts` runs the agent's own lookup tools (`plan_sailings`, `find_backup_drivers`, the hotel quotes) without a model, so it is free and instant. It checks later sailings, free drivers near the pickup (or near the buyer after collection), a hotel if a plan needs a night, and what each plan means for the promise. Out of that come two or three options with arrival, cost (quoted or clearly marked as an estimate), certainty and risk. Delivered or cancelled orders, and orders where nothing useful turns up, say plainly that there is no safe Plan B. It never books, cancels, prices or sends anything, and it says so on screen.
- *Priority changes the advice, not just the order.* `lib/agent/priority.ts` ranks on the options' own numbers and explains each one against the others, for example "Gets there 3.5 days later than the fastest option" or "About €953 more than the cheapest option". The trade-off is spelled out under the switch. The server ranks Plan B by the priority it is sent. Choosing an option tells the agent which priority made the difference, and "Hand to the agent" starts a case with the option and the priority in its brief.
- *The timeline now tells the whole story:* what went to plan, where it went wrong, what the agent checked, when Plan B was prepared, and what the operator decides next.
- *The look:* one alarm colour in the control room (at-risk differs from critical by weight, not hue), green only for confirmed, and a muted indigo for everything the agent does. Queues are dense rows divided by hairlines instead of floating cards. The on-track panel sits on a quieter background in smaller type. The selected order is one workspace with a header, the timeline as its spine, then the chapters, with no boxes inside boxes.

**Step 9: show less, so the decision stands out.** Manas found the workspace far too much to read: long timelines, every piece of evidence and the agent's whole trace, all at once. The point of the agent is to do the reading first. So the workspace now answers four questions without a click (what is wrong, what the agent found, what you need to decide, and what Speed, Cost or Certainty changes) and folds everything else behind one line.
- *Order of a problem case:* headline, then the countdown to the next deadline, then "What should we optimise for?", then the recommended option for that priority with its approve controls, then the journey, then Plan B, then folded sections. The full order is visible in one screen on a laptop.
- *The recommendation follows the priority.* The top-ranked option is shown in full: why it fits, delivery, cost, certainty and whether it needs approval. When it is not the agent's own pick, the page says where the agent's pick ranks, and "Approve the agent's pick" stays one click away. The other options fold into one line ("2 other options, ranked for cost: …") and open for comparison.
- *A horizontal journey.* The vertical timeline became a left-to-right line of key points: where it started, the last confirmed step, every decision, the latest problems, the agent's work and Plan B, now, and what comes next. Everything else collapses into "+N" markers and a "+ N more updates" switch. Hover, keyboard focus or a tap opens a small card under the line with the time, what happened and the source. The point that needs a person is drawn bigger with a ring; nothing else on the page turns red because of it. On narrow screens the line scrolls sideways and starts with "now" in view.
- *One line per supporting section.* "Agent checked 14 sources and found no open conflict. Show evidence", "Agent activity: 26 steps. Latest: …", "Latest update: … View full history", plus the deadlines, the site pattern and Plan B's checks. They are native `<details>` elements, so they work with the keyboard and screen readers, and nothing is nested two deep.
- Nothing underneath changed: the same data, agent, approvals, Plan B lookups and timeline entries. It is only what is shown first.
- *Follow-up: a compact Needs attention list.* Each row now shows only the car and route, Critical or Not critical, the time left (the agent's countdown, or the order's next decisive date while it is still ahead), and whether a person has to decide. That is the case when the agent's hand-over waits, the agent stopped, or another agent left a proposal to review. The selected row is framed so it stands out. The column went from 320–380 px to 320 px (300 px on narrower desks), still wider than the 296 px On track panel. The workspace and everything else is unchanged.
- *Follow-up: All orders as one donut.* The lane columns were a wall of cards. The page is now a donut of the board's own seven lanes (`LANES` in `lib/present/labels.ts`), with counts from the overview API, next to a compact list of orders. Clicking a segment or its legend row selects that lane ("Ready to post — 12 orders"), dims the rest and lists only those orders, and "Show all orders" goes back. Each row is the car, the route, the reference, the lane, and a "Needs a person" flag, and it opens the order record as before. Search and the "Needs a person" toggle narrow the chart and the list together. The chart is plain SVG, with no new dependency. Segments are keyboard buttons with a tooltip on hover or focus, and the legend gives the same numbers in words. The seven colours were checked with a palette validator: neighbours stay apart for colour-blind readers, and Cancelled is a hatched grey on purpose. "Needs a person" stays a toggle rather than a segment, because those orders also sit in a lane and would be counted twice.
- *Follow-up: compare several lanes.* A plain click on a segment still picks just that lane. Shift-click (or Shift+Enter) adds or removes one, and every legend row has a checkbox that does the same, for touch and keyboard. The list joins the picked lanes in pipeline order, with no duplicates. The heading names them ("Ready to post + Moving — 36 orders"), or counts them past three. "Show all orders" moved next to the chart's title and clears every pick.
- *Follow-up: a top bar and pill buttons.* The left sidebar became one slim bar across the top. It holds the wordmark, the same six sections in their two groups (split by a hairline where the group labels used to be), and the snapshot time and Easy reading switch at the far end. Every page gets the full width back. On a phone the sections scroll sideways. Every real button is now a pill: actions, Approve and Reject, the Speed/Cost/Certainty switch (a pill track with the chosen pill filled), "Show all orders", the filters, back links and the expand/collapse controls. Cards, rows, inputs, panels and chart segments keep their square corners, so a pill always means "press". Primary is solid ink, secondary is outlined, quiet is plain text, and Reject is red text that turns into a solid red pill when you confirm it.
- *Follow-up: the sidebar is back.* The top bar did not feel right, so the left sidebar returned exactly as it was before (same file, same styles). The pill buttons stayed. The control room's own "Control room" heading duplicated the sidebar's wordmark, so it is now visually hidden but kept for screen readers as the page's heading.

**Step 11: the case in a few seconds.** Manas still found too many pieces of text saying the same thing on a problem case. The operator should not have to read everything before acting, because the agent has already done the reading. The default view now answers five questions and nothing else: what is wrong, what is the next deadline that cannot be undone, what should we optimise for, what is the recommended action, and what needs approving.
- *Header.* One short label ("Act now", "Decide today", "Needs your decision"), the car and route as the title ("BMW M4 · Helsinki → Turku"), and one issue sentence. That sentence is the agent's headline without its question or its own countdown, which went stale and disagreed with the clock. The agent's longer situation paragraph moved into the evidence section, together with its "effect on delivery" note.
- *One deadline.* It shows the soonest deadline still ahead, with one line on what happens after it. The agent does not always list deadlines in time order, so `nextDeadline` now sorts them, and the queue rows follow the same rule. The other deadlines are behind "View all milestones".
- *One recommendation card.* It shows the concrete step (the first sentence of the option's plan), one impact line (delivery · estimated extra cost · certainty · whether a person must approve), and three buttons: Approve plan, Edit plan, Reject. "Choose this", "I did the agent's pick" and "Do something else" are gone. Under the hood nothing changed. Approving the agent's own pick approves it, and a step the operator does themselves still asks how it went first. Approving any other option still goes back to the agent as "do this instead". Edit plan opens the same "what should happen instead" form with the plan filled in to change. Every other option, including the agent's pick when it ranks lower, sits behind "2 other options · Compare options" with its full reasoning and its own Approve plan button. The customer message still shows next to whichever button would send it.
- *Everything else is one line, one click.* Evidence ("Agent checked 16 sources and found no open conflict"), Plan B (it was a big panel, now its first sentence with the agent's plan, the switch button and the lookups inside), all milestones, the full delivery timeline, the site pattern, the agent trace and the order history. The journey line mounts when it is opened, so it still measures itself and scrolls to "now". The lookup bursts in the agent trace and Plan B's "what was checked" are no longer folds inside folds. The order record keeps its own sections, since it is the same view as the full record page.
- The order without an agent case uses the same header, deadline, card and folds, and keeps "Hand to the agent", because there is nothing to approve yet.
- Small fix from step 10: on a phone the Bahn logo shrank under the first nav pill in the top strip. It now keeps its size and drops the "Control Room" text there.
- No change to the agent, recovery ranking, Plan B lookups, approvals, API, prompts or database.

**Step 12: one palette for the whole interface.** Manas supplied a palette (Bahn red #df2531, the same red at 65% and 45% over black, white and black) and asked for a visual system built only from it, one that feels like a deliberate operations tool rather than a generated dashboard. This step changes the look only.
- *Tokens.* `globals.css` now starts its last section with the five palette colours (`--pal-*`) and named UI roles (`--ui-bg`, `--ui-sidebar`, `--ui-panel`, `--ui-text`, `--ui-text-muted`, `--ui-border`, `--ui-accent`, `--ui-selected`, `--ui-danger`, `--ui-success`, `--ui-agent` and so on). The older token names the file already used (`--ink`, `--hair`, `--red`, `--green`, `--agent`…) point at those roles, so every existing rule follows without being rewritten. The only other tones are palette colours at lower opacity: greys are black at 3–78%, and tints are red over white. Lane colours (`--lane-*`) feed the donut, the legend and the lane dots.
- *Hierarchy.* The workspace is white, with black text doing the work. The sidebar is the one black surface, and it uses the light Bahn logo. Red is kept for what needs a person: the primary action (Approve plan, Hand to the agent), the current page in the sidebar, critical marks and the deadline. "At risk" uses the deeper red. Selection inside the workspace (the chosen priority, the selected queue row) is black, so red keeps its meaning. Panels get depth from a 3% tint and one soft shadow on the recommendation card, not more borders.
- *No green or blue.* Confirmed and on-track states are black with their check icon and label. The agent's own work is a quiet grey with its bot icon. Every status keeps its text or icon, so none depends on colour.
- *Contrast.* Body text is black on white. Muted text is 6.6:1 and labels are 4.9:1 on white, and critical text uses the 65% red (8.9:1). Sidebar text is white at 72%, white on the red pill is 4.6:1, and focus rings are black in the workspace and white in the sidebar. Easy reading and the responsive layout are unchanged.
- Two layout fixes found while checking: an opened delivery timeline could widen the case column (fold items now have `min-width: 0`), and the queue's critical edge is the deep red so forty rows don't all shout.
- *Follow-up: fold away On track.* A small pill at the head of the On track panel folds it to a 52 px rail, and the case workspace widens into the space. The rail keeps the pill and the count, so the panel is one click from coming back. The list stays mounted while folded, so the selection, search and lane groups are untouched, and its scroll position is put back on reopen (once straight away, and again after the column finishes widening, because the text rewraps as it grows). On narrower desks, where the panel sits under the queue, and on phones it folds to its heading instead. The width change is a 0.2 s transition, which is switched off under reduced motion. The pill is labelled "Collapse On track" or "Show On track" and reports `aria-expanded`. It always starts open.
